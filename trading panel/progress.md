## Stage 1 of the big plan — audit DONE (no code changed), findings below, fixes not yet decided

**Security — `redeem` rate limiting: 🔴 real gap, highest priority of everything found in this audit.**
- No rate limiting anywhere (not in the Edge Function, not in Supabase config, no client-side throttling in `useRedeemCode.ts`/`AccessCodeModal.tsx`).
- More serious than "just" brute-force risk: `redeem/index.ts:130-146` — redeeming an **already-claimed** code just issues a fresh JWT for that same account (up to `MAX_DEVICES_PER_CODE`=2 devices) with no ownership check. Since a code is the *only* credential in this product (no separate password), a correctly-guessed already-sold code = full takeover of that customer's trading data, not just a tier upgrade.
- Error responses are distinguishable (404 unknown code / 400 wrong kind / 403 device-limit-hit / 200 success) — no obfuscation, straightforward to script through code space by status code.
- `access_codes.code` has no CHECK constraint on length/format (`001_init_schema.sql:18-23`) — nothing in the schema guarantees future codes (e.g. a promo code) keep the same high entropy as today's 16-char `XXXX-XXXX-XXXX-XXXX` samples.
- **Recommended fix (not built)**: server-side attempt-tracking table (`redeem_attempts`, keyed by deviceId/IP, temp-lockout after N failures in a time window) inside the Edge Function itself. Client-side backoff is a weak second layer only (trivially bypassed via direct curl).

**Accessibility — biggest finding: no modal in the app closes on Escape, and none trap/move focus on open.**
- Confirmed via grep across the whole codebase: zero `Escape`/`keydown` handling near any `role="dialog"`.
- Affects: `AccessCodeModal.tsx:30`, `TradeForm.tsx:492-502` (chart-image lightbox — **keyboard-only users cannot close this at all**, no X button either), `ChartImageThumbnail.tsx:49` (same lightbox pattern), `DailyTradingView.tsx:41` (has an X button so partially reachable, but no Escape, no focus moved into the dialog on open), `PrivacyPolicy.tsx:15`, `TermsOfService.tsx:15`.

- Medium: `PillNav.tsx` active tab has no `aria-current`/`role="tab"` (CSS-only `data-active`, invisible to screen readers); toggle buttons (Long/Short in `TradeForm.tsx`, filter segments in `TradeList.tsx`) use `data-active` without `aria-pressed`; `WorkspaceSettings.tsx:779-784`'s delete-confirmation text input has no associated `<label>`.

## Redeem rate limiting — FIXED (code done, reviewer-approved), migration NOT run yet
User chose to fix this immediately rather than defer. New `supabase/029_redeem_rate_limit.sql` (not run yet — user action required): `redeem_attempts` table (`device_id`, `attempted_at`, `success`), RLS locked to service_role only (same pattern as `access_codes`), indexed on `(device_id, attempted_at)`. `redeem/index.ts`: before any `access_codes` query, counts failed attempts for that `deviceId` in the last 10 minutes (`RATE_LIMIT_WINDOW_MINUTES`); ≥5 failures (`MAX_FAILED_ATTEMPTS`) → immediate 429, fail-fast (never touches `access_codes`, so it can't be used to enumerate whether a code exists). Every exit point (success, code-not-found, wrong-kind, device-limit-hit on both retry paths) now calls `recordRedeemAttempt`. Both new functions are best-effort (try/catch, same principle as `slTpHistoryApi.ts`) — a bookkeeping failure never blocks a legitimate redeem.
- **Reviewer pass (auth-adjacent, required per project convention) — approved, no blocking issues.** Confirmed: RLS correctly locked, no client-visible enumeration, no race condition in the count query, backward-compatible (response shape unchanged). Two non-blocking notes: (1) `deviceId` is client-supplied and could be spoofed via private browsing/localStorage+cookie+IndexedDB clearing to reset the per-device counter — inherent limitation of a device-based (not IP-based) scheme, still a real improvement over the prior zero-protection state; (2) a legitimate user who fat-fingers a code 5 times in 10 minutes gets locked out even on a correct 6th attempt — considered an acceptable tradeoff, not changed.
- `npx tsc --noEmit` clean, `npm run build` succeeds (Edge Functions are Deno, not part of the app's tsconfig — not applicable to that half of the diff).

## 🔴 Critical purchase-flow bug found + fixed: redeeming a genuinely fresh (never-before-used) access code was completely broken
Discovered when the user asked for two personal access codes (`NOAM-BASIC-0001`/`NOAM-PRO-0001`, `unlimited_devices=true`) to test with, separate from the `DEVP`/`DEVB` dev codes used throughout this session's testing — those dev codes were always already-redeemed from repeated earlier testing, so they only ever exercised `redeem/index.ts`'s "already redeemed by someone" branch. A truly fresh code exercises a different branch, and that branch had a real bug: `supabase/functions/redeem/index.ts` (the "claim an unredeemed code" UPDATE) did `.select('id')` on `access_codes` — but that table has **no `id` column at all** (its primary key is `code` itself, per `001_init_schema.sql`). Every attempt to redeem a brand-new code failed with a raw Postgres error. This was additionally masked by the `errorMessage()` bug fixed earlier in this session (only unwraps `instanceof Error`) until `redeem` was redeployed with that fix — first symptom was the generic "שגיאה לא ידועה", the real error (`column access_codes.id does not exist`) only surfaced after redeploying `redeem` with the already-fixed shared `errorMessage()`.

**This means, in principle, this exact bug would have blocked every real first-time customer from ever redeeming a purchased code** — it was never caught before because all prior live testing in this project's history reused the same handful of dev codes, which were always already-claimed after their first use.

Fixed: `.select('id')` → `.select('code')` (comment updated to explain why, cross-referenced to the schema). Deployed and live-verified end to end with both fresh personal codes: `NOAM-PRO-0001` → new distinct account, `Current plan: PRO` confirmed in Settings; `NOAM-BASIC-0001` → new distinct account, "Upgrade to Pro" pill confirmed (Basic tier). Both codes remain unredeemed-and-reusable in the sense that they're the user's own personal ones (`unlimited_devices=true`, not shared with dev/test accounts) — not touched by any agent testing going forward per the user's explicit request.
